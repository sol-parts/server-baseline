# sol.parts Server Baseline

Базові вимоги й Ansible-роль для сервера, на якому працюватиме магазин на
платформі [sol.parts](https://sol.parts).

Репозиторій відповідає на одне питання: **що має бути на сервері, щоб магазин
на ньому запрацював**. Він призначений тим, хто розгортає магазин на власному
сервері й хоче зробити це самостійно або силами свого адміністратора.

## Кому це потрібно

Магазин на платформі sol.parts живе на окремому сервері зі своєю базою.
Сервер можна взяти двома способами:

| | Власний сервер | Керований сервер |
|---|---|---|
| Хто замовляє інфраструктуру | ви | sol.parts |
| Хто адмініструє ОС, оновлення, копії | ваш адміністратор | sol.parts |
| Цей репозиторій | ваш вихідний стан | не потрібен |

## Що робить роль

- **Система**: часова зона, EPEL/CRB, утиліти для роботи з прайсами
  (`unzip`, `p7zip`, `enca`, `xlsx2csv`) і зображеннями
  (`ImageMagick`, `jpegoptim`, `webpmux`, `libvips`), `rclone` для копій фото.
- **PHP 8.2** (SCL-збірка Remi, паралельна до системного PHP) з розширеннями,
  які вимагає платформа, окремим пулом PHP-FPM і налаштуваннями
  `php.ini`, без яких магазин працює неправильно.
- **MariaDB 10.6** з `utf8mb4`, повнотекстовим пошуком по коротких токенах
  (артикули на кшталт `M8`, `R15`) і не-строгим `sql_mode`.
- **nginx**: vhost магазину, HTTP/2, TLS-профіль Mozilla intermediate,
  віддача зображень із підміною `webp`/`jpg`, кешування складених асетів,
  сторінки помилок.
- **Meilisearch** як systemd-сервіс: без нього вітрина не шукає товари.
- **Let's Encrypt** через webroot + автопродовження.
- **firewalld**: відкриті `http`, `https`, `ssh`.
- **Ротація логів** сайту (логи лежать поза `/var/log`, тож дистрибутивні
  правила їх не бачать).
- **Runtime магазину** (опційно, після розгортання коду): обгортка консольних
  команд і systemd-юніти воркерів черги.

## Швидкий старт

Перевірена ОС — **AlmaLinux 9**. Роль прийме будь-який дистрибутив сімейства
RHEL 9, але робочих магазинів на інших ми не тримаємо, тож рекомендуємо саме
AlmaLinux. На чужому сімействі роль зупиниться, а не спробує «якось»
відпрацювати.

```bash
git clone https://github.com/sol-parts/server-baseline.git && cd server-baseline
```

```bash
ansible-galaxy collection install -r requirements.yml
```

```bash
cp inventory.example.yml inventory.yml && ${EDITOR:-vi} inventory.yml
```

```bash
ansible-playbook playbook.yml
```

Перевірити результат, нічого не змінюючи:

```bash
ansible-playbook playbook.yml --tags verify
```

Окремі частини — за тегами: `system`, `site`, `php`, `mariadb`, `meilisearch`,
`nginx`, `tls`, `firewall`, `logrotate`, `runtime`, `verify`.

## Перевірка сервера без Ansible

Якщо сервер уже налаштований (вручну, іншим інструментом, або це чужий сервер,
який треба оцінити) — скрипт нічого не змінює, лише звіряє стан із вимогами:

```bash
curl -fsSL https://raw.githubusercontent.com/sol-parts/server-baseline/main/scripts/check-server.sh | bash
```

Скрипт корисний і як список вимог у машинному вигляді: дивіться його вихідний
код, якщо ставите все руками.

## Чого тут свідомо немає

Роль закриває базові вимоги платформи до сервера. Далі починається робота,
яку не можна зробити «за замовчуванням» — вона залежить від профілю трафіку,
каталогу й моделі загроз конкретного проєкту:

- захист від ботів і скрапінгу, rate limiting, tarpit, WAF;
- fail2ban та реакція на розподілені атаки;
- CDN, зовнішній проксі, віддача зображень з об'єктного сховища;
- тюнінг MariaDB під конкретний профіль запитів, реплікація;
- моніторинг, збір метрик, алерти;
- схема резервного копіювання й перевірка відновлення;
- поштовий стек (SPF/DKIM/DMARC, репутація домену);
- посилення SSH та політика доступів.

Це не «дрібниці, які додасте потім»: під реальним трафіком магазину саме вони
визначають, чи буде сайт доступним. Плануйте цю роботу зі своїм
адміністратором або розгляньте варіант керованого сервера.
