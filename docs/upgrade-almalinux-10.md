# Оновлення AlmaLinux 9 → 10

Як перевести вже налаштований сервер магазину з AlmaLinux 9 на 10 на місці,
без переїзду на нову машину. Інструмент — ELevate (leapp) від AlmaLinux.
Документ про сервер, який налаштувала ця роль або який зібрано вручну за
[manual-install.md](manual-install.md).

Під час оновлення магазин не працює; закладайте вікно щонайменше на годину.
Довше буде на сервері з великою кількістю файлів: після першого завантаження
AlmaLinux 10 система перемарковує всі файли для SELinux (розділ «Чого
очікувати»).

Команди — від `root`.

## 1. До старту

- **Знімок диска в хостера.** Це ваш відкат: оновлення на місці не має кнопки
  «скасувати». На виділеному сервері знімка немає — зробіть копію бази й
  файлів сайту на іншу машину (розділ «Виділений сервер»).
- **Спершу PHP 8.4 і MariaDB 10.11 ще на AlmaLinux 9.** Роль версії 1.3.0
  ставить їх за замовчуванням; перехід на них окремим кроком означає, що в
  день оновлення ОС змінюється лише ОС. Після переходу на MariaDB 10.11 —
  `mariadb-upgrade`. Перевірка:

  ```bash
  ansible-playbook playbook.yml --tags verify
  ```

- **Вільного місця на `/` — щонайменше 5 ГБ.** leapp завантажує пакети
  AlmaLinux 10 на той самий диск, а нестача місця виявиться вже тоді, коли
  магазин зупинено.
- **Пам'ять.** На сервері з 4 ГБ RAM і менше leapp не вистачає пам'яті на
  підготовку пакетів. Додайте тимчасовий swap на час оновлення:

  ```bash
  fallocate -l 4G /swap_leapp && chmod 600 /swap_leapp && mkswap /swap_leapp && swapon /swap_leapp
  ```

- **Система оновлена й перезавантажена на найновіше ядро:**

  ```bash
  dnf update -y && reboot
  ```

## 2. ELevate і перевірка без змін

```bash
dnf install -y https://repo.almalinux.org/elevate/elevate-release-latest-el9.noarch.rpm
dnf install -y leapp-upgrade leapp-data-almalinux
leapp preupgrade
```

`leapp preupgrade` нічого не змінює: він збирає звіт у
`/var/log/leapp/leapp-report.txt`. Пункти з позначкою `(inhibitor)` блокують
оновлення — їх треба прибрати й запустити `preupgrade` ще раз. Магазин увесь
цей час працює.

`dnf install` вже встановлений пакет не оновлює. Якщо ELevate ставили під час
попередньої спроби, перед новою оновіть його:

```bash
dnf upgrade -y leapp-upgrade-el9toel10 leapp-data-almalinux
```

Інгібітори, які трапляються найчастіше:

| Що в звіті | Як прибрати |
|---|---|
| мережеві профілі у форматі `ifcfg` | `nmcli connection migrate` для **кожного** файла `/etc/sysconfig/network-scripts/ifcfg-*`, не лише `eth0` |
| абсолютні символьні посилання в корені `/` | замінити відносними (`ln -snf <ціль без початкового /> /<посилання>`) або прибрати |
| порядок рядків у `/etc/fstab` | `/` має стояти раніше за `/proc` і `/boot` (буває в образах хостерів) |
| рядки `/etc/fstab` для дисків, яких уже немає | прибрати ці рядки |
| `The installed OS version is not supported for the in-place upgrade` | Буває в перші тижні після виходу нового мінору AlmaLinux 9: `dnf update` уже перевів на нього систему, а ELevate ще не додав його підтримку (так було з 9.9 до ELevate 0.25). Відкотити мінор не вийде: дочекайтеся нової версії ELevate (`dnf --refresh list --available leapp-upgrade-el9toel10`), оновіть пакети командою вище й повторіть `preupgrade` |

Попередження без позначки `inhibitor` (застарілі драйвери, модель процесора
поза списком підтримки RHEL 10) оновленню не заважають.

## 3. Оновлення (магазин не працює)

1. **Копія бази** — свіжий дамп на той самий сервер і бажано ще кудись:

   ```bash
   mysqldump --single-transaction --quick --routines --events <база> | gzip -1 > /root/<база>-before-el10.sql.gz
   ```

2. **Прибрати пакети сторонніх репозиторіїв.** leapp оновлює лише те, що
   знає, а PHP із Remi, nginx із nginx.org і MariaDB з mirror.mariadb.org
   зібрані під AlmaLinux 9. Після оновлення роль поставить їх версії під
   AlmaLinux 10. Дані бази (`/var/lib/mysql`), конфіги сайту й код
   магазину при видаленні пакетів лишаються на місці.

   Список будуйте за репозиторієм, з якого пакет встановлено, а не за маскою
   імені: з Remi приходять і `vips` та бібліотеки до PHP, з MariaDB — `galera-4`.

   ```bash
   dnf repoquery --installed --qf '%{name} %{from_repo}\n' \
       | awk '$2 ~ /^(remi|nginx-stable|mariadb)/ {print $1}' \
       | sort -u > /root/el9-third-party.txt
   cat /root/el9-third-party.txt                      # перегляньте перед видаленням
   dnf remove -y $(cat /root/el9-third-party.txt) remi-release
   rm -f /etc/yum.repos.d/mariadb.repo /etc/yum.repos.d/nginx-stable.repo
   ```

3. **Оновлення й перезавантаження:**

   ```bash
   leapp upgrade && reboot
   ```

   Сервер перезавантажиться в середовище оновлення, встановить пакети
   AlmaLinux 10, перемаркує файли для SELinux і перезавантажиться ще раз уже
   в нову систему. Спостерігати зручно в консолі хостера; **не
   перезавантажуйте сервер вручну**, поки йде перемаркування (див. «Чого
   очікувати»).

## 4. Після завантаження AlmaLinux 10

```bash
cat /etc/almalinux-release                               # AlmaLinux release 10.x
dnf config-manager --set-disabled elevate elevate-source  # репозиторій ELevate більше не потрібен
```

Вимкніть репозиторій ELevate до наступного кроку: якщо його дзеркало в цю
хвилину недоступне, перша ж установка пакетів падає, і магазин лишається без
PHP, nginx і MariaDB.

EPEL 10 збирається під кожну мінорну версію ОС окремо, а на AlmaLinux 10 він
за замовчуванням бере гілку під CentOS Stream (`epel-10s` чи схожу), на мінор
попереду системи. Пакети звідти можуть не ставитись через залежності
(наприклад, certbot). Роль з версії 1.3.2 прив'язує EPEL до мінору ОС сама;
без ролі (або зі старішою версією) зробіть це вручну:

```bash
sed -i 's/\$releasever\${stream:+s}/$releasever_major.$releasever_minor/' /etc/yum.repos.d/epel.repo
dnf clean all
```

Далі — повний прогін ролі, вона поставить стек під AlmaLinux 10:

```bash
ansible-playbook playbook.yml
```

Після ролі:

```bash
mariadb-upgrade
systemctl restart mariadb nginx php84-php-fpm meilisearch
systemctl restart 'sol-messenger-*'          # якщо увімкнено блок runtime
ansible-playbook playbook.yml --tags verify
```

Перезапуск потрібен, якщо прогін ролі переривався: обробники, що мали
перезапустити службу після зміни конфігу, тоді не спрацювали, а повторний
прогін їх уже не викличе — служба лишається на старому конфігу.

Без Ansible — та сама послідовність за [manual-install.md](manual-install.md)
(команди там для AlmaLinux 9 і 10) і перевірка `scripts/check-server.sh`.

## 5. Прибирання

Через тиждень спокійної роботи:

```bash
rpm -qa | grep -E '^(leapp|python3-leapp)' | xargs -r rpm -e --nodeps
dnf remove -y leapp-deps-el10 leapp-repository-deps-el10 elevate-release
dnf remove -y $(rpm -qa | grep '\.el9')
rm -rf /var/lib/leapp /var/log/leapp /etc/leapp
swapoff /swap_leapp 2>/dev/null; rm -f /swap_leapp
dnf clean all
```

Пакети leapp видаляйте першими й окремо: одна спільна транзакція з рештою
залишків AlmaLinux 9 падає з «conflicting requests» і не видаляє нічого.
Потім — знімок у хостера й дамп бази, якщо вони більше не потрібні.

## Чого очікувати

- **Після першого перезавантаження сервер довго недоступний.** Встановлення
  пакетів AlmaLinux 10, перемаркування і друге завантаження йдуть без SSH і
  сайту — від кількох хвилин до пів години й довше. Тривалість залежить від
  швидкості диска і кількості файлів на ньому: якщо фото товарів лежать на
  диску сервера, файлів сотні тисяч і більше, а з фото в об'єктному сховищі
  (S3) цей етап проходить у рази швидше. Поки на графіку диска в панелі
  хостера є запис або рівне читання, сервер працює — не перезавантажуйте його.
- **Перемаркування SELinux.** На першому завантаженні AlmaLinux 10 система
  проходить кожен файл на диску (`selinux-autorelabel`). Час залежить від
  **кількості файлів**, а не від обсягу: якщо фото товарів лежать на сервері,
  а не в об'єктному сховищі, — від 20 до 45 хвилин і довше. У консолі видно
  `Relabeling / /boot …`, на графіку диска в панелі хостера — рівне читання
  в кілька сотень операцій на секунду. Перезавантаження посеред процесу
  запускає його спочатку.
- **Сервер може не перезавантажитися після встановлення пакетів.** Трапляється
  на деяких VPS: ping є, усі порти закриті, консоль не відповідає на
  клавіатуру, а графік диска понад 15 хвилин стоїть біля нуля. Тоді
  перезавантажте сервер **коректно** — кнопкою Ctrl+Alt+Del у консолі
  хостера, не скиданням живлення; далі піде перемаркування і нормальне
  завантаження. Поки на графіку тисячі операцій запису — leapp ще працює,
  нічого не чіпайте.
- **Консоль заливають повідомлення про старт воркерів.** Воркери черги
  перезапускаються кожні 30 секунд, поки немає PHP. Це не помилка і не
  ознака того, що система вже завантажилась.

## Виділений сервер (RAID1)

Оновлюйте з **цілим** масивом: leapp сам встановлює завантажувач на всі
диски, з яких зібрано `/boot`. Від'єднаний «як відкат» диск ненадійний:
система може завантажитися саме з нього, а масив — повернути його й
синхронізувати, і копія старої системи зникне.

Відкат для виділеного сервера — копія бази й файлів сайту на іншій машині.
Якщо на цій машині розгорнуто ще й код магазину, вимкніть на ній крон і
воркери черги, інакше вона паралельно з основним сервером завантажуватиме
прайси й надсилатиме листи.

Після оновлення перевірте масиви й завантажувач:

```bash
cat /proc/mdstat                 # усі масиви [UU]
grubby --default-kernel          # ядро el10
```
